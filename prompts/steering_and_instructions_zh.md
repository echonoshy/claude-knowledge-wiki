# Notebook 中的引导指令、启动消息与存储挂载说明 · 中文版

> 原文均定义在主 Notebook（`distill_documents_into_knowledge_wiki.ipynb`）的代码单元格中，未单独存放在 `prompts/` 目录。（仅供阅读对照，不用于实验运行）

## 1. `STEERING` · 汇总阶段引导指令
> 注入 `analyzer_system.md` 和 `organizer_system.md` 末尾的 `<instructions>` 块中，让通用的整合流程聚焦这笔并购尽调交易。

在常规汇总工作之外，还须完成以下 6 项要求：

1. **归档位置（PLACEMENT）**：关于某个人或实体的每一条事实，都必须出现在该实体自己的文件里，即使别处已经记录过——只读单个实体文件的分析员绝不能漏掉与它有关的事实。
2. **疑点清单（`escalations.md`）**：在存储根目录维护 `escalations.md`：按重要性排列的清单，列出尽调团队应当上报的每一项红旗疑点（包括：原因不明的所有权变化、交易待决期内内部人士的售股/赠股/交易计划、未披露的法律实体名称、同一文件内部前后不一致、指标定义冲突），每条附一行“为什么重要”说明及完整出处。核对助手（analyzers）用定向编辑添加条目，整理助手（organizer）对整张清单统一排序。
3. **人物疑点（Red flags）**：在每个人的实体文件中，若存在适用疑点，添加 `## Red flags` 小节并注明出处。
4. **链接结构（LINK STRUCTURE）**：本存储采用 Agent Knowledge 格式——带 YAML 文件头的 Markdown 节点，以 `[[wikilinks]]` 作为边。汇总时修复链接结构：正文中每次提到实体都应写成 `[[wikilink]]`；指向缺失节点的 `[[redlink]]` 意味着要补建该节点或记录为何无法存在；保持文件头的 `name`/`aliases` 与文件名一致；链接一律写裸标识（`[[permira]]`），绝不写路径或文件名。
5. **重复项合并（DUPLICATES · 由整理助手执行）**：
   - 当发现两份文件其实是不同拼写下的同一个现实实体或同一份文档（连字符/下划线/后缀变体、项目代号）时，它们应合并为一个节点：按 `_schema.md` 的 slug 规则合并到规范标识中，保留每一条事实和来源行，把被并入的拼写记入保留节点的 `aliases`，在旧位置留一行 `MOVED TO` 占位，然后全库 `grep` 搜索 `[[old-slug]]` 并将所有命中改指向保留标识。
   - 文件里自称“重复”的备注只是核查线索，不是证据——只合并你亲自核实确认的重复项，并删掉错误的重复备注。
   - 一个现实名称只归属于一个节点：如果两个节点列出了相同的别名，判断它真正指代谁，并从另一个节点移除。
   - `SKILL.md` 和 `_index.md` 只描述运行结束后移除 `MOVED TO` 占位之后存储里**实际保留**的内容：不含占位，不含不存在的文件。
6. **阅读成本优化（READING COST · 核对助手先做，整理助手收尾）**：分析员要为读到的每一行付费，并且会先读文件顶部再看下文。
   - **(a) `_index.md`**：开头设 `## Where to start` 小节，不超过 **40 行**——每个主题领域占一行，点出最先应打开的 1 到 3 个节点（核心枢纽实体、交易事件节点、`escalations.md`）及各自能回答什么问题；其后在各 `##` 标题下跟逐文件总目录。
   - **(b) 长节点**：凡是体积超过约 **8,000 字符** 的节点（无论它实际有多少行），在 YAML 文件头紧接着加 `## Current picture` 小节，不超过 **30 个短行**、总计约 **3,000 字符**：优先放分析员最可能想看的事实和最新现行值（每条附 `[source | as-of]`）；下文记录的每个 `CONFLICT` 标记和每个已失效数值各占一行；最后一行列出该节点的其他 `##` 章节名。详细内容留在下方的主题 `##` 标题下，每行一条事实，每行不超过一两句话，方便读者按标题或关键词定位并只读那几行。
   - **(c) `escalations.md`**：在完整条目之前先放一份摘要（digest），每项排好序的疑点占一个短行（编号、标题、涉及实体）。

## 2. `build_request` · 发送给统筹助手的启动任务消息
> 建库会话中发送给 `wiki-builder` 的唯一一条 `user.message`。各阶段的先后顺序由这几句话里的依赖关系自然决定。

```text
根据挂载在 /mnt/session/uploads/corpus 下的源文档，在 {mem_dir} 构建知识库；源文档按下方列出的批次目录分组：

<batches>
/mnt/session/uploads/corpus/batch-01
...
/mnt/session/uploads/corpus/batch-25
</batches>

你有四个预定义助手：
- "wiki-extractor" 读取一批文档，并将其所述内容归档进知识库。
- "wiki-resolver" 在所有批次都提取完成后，处理知识库中的未决问题。
- "wiki-analyzer" 在补查助手完成后，对照知识库重读一批文档并补上遗漏的内容。
- "wiki-organizer" 在核对助手完成后，整理整个知识库。

请把这些作为一次工作流运行来执行，结束后告诉我发生了什么。
```

## 3. 记忆存储挂载说明（`*_INSTRUCTIONS`）
> 创建会话挂载 Memory Store 时，随挂载路径一起展示给助手的简短说明。

- **`STORE_INSTRUCTIONS`（建库会话 · 读写挂载）**：
  > 交易知识库。其布局和写入规则位于根目录的 `_schema.md`。

- **`WIKI_INSTRUCTIONS`（知识库答题会话 · 只读挂载）**：
  > 只读交易知识库。`_index.md` 开头有“从哪里开始”的导航图；节点文件存放在 `entities/` 下（每个实体、合同或文档分片一个文件），旁边配有逐文档的 `relations/`、`metrics/` 和 `open_questions/` 文件；长节点开头带有 `Current picture` 概况，`escalations.md` 开头是排好序的疑点摘要，`_schema.md` 说明整体布局：先读文件顶部，再只读需要的章节。事实带有 `[source | as-of]` 出处——请引用它。如果知识库没有答案，请说 `"Not in the wiki"` 并指明需要的文档。

- **`RAW_INSTRUCTIONS`（费用对比原文对照会话 · 只读挂载）**：
  > 以文本文件形式保存的原始交易资料室文档（大型申报文件已拆分为 `.partN` 文件）。搜索并阅读需要的段落；引用源文件。如果文档没有答案，请说 `"Not in the data room"`——绝不猜测。
